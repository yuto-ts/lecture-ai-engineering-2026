### やったこと

ベクトル検索の各ヒットに、同じ資料の前後1ページの本文を付けて返す取得処理を追加しました。本文・埋め込み・索引は変えていません。

| ファイル | 変更内容 |
|---|---|
| `app/retrieval.py` | `search_with_neighbors()` を追加。`search()` の上位5件それぞれについて、`load_pages()` の並びで前後 `RAG_NEIGHBOR_WINDOW` ページを取り出す。`document_id` が違うページは付けない。同じページは1回だけ返し、検索ヒットは `role="hit"`、補ったページは `role="neighbor"` と `neighbor_of` を付ける。`python -m app.retrieval --neighbors "検索語"` で検索だけを確認できる |
| `app/config.py` | `RAG_NEIGHBOR_WINDOW = 1` を追加 |
| `app/tools.py` | `search_materials_with_neighbors()` を追加。docstring に、前後ページは検索で選ばれたページではないので関係するときだけ根拠に使う、と書いた |
| `app/agent.py` | `--neighbors` を追加。ツール名を `search_materials` のまま中身だけ差し替え、`INSTRUCTIONS` は変更前と同じものを使う。`--trace` で、返ったページIDの一覧（前後ページには「(隣)」）を表示するようにした |

#### Q2：必要なページは変更前からそろっていた

変更前の検索結果に、答えを支える p.13、39、40 がすべて入っていました（ほかに p.38、65）。変更後は p.12、14、37、41、64、66 が加わりましたが、どれも回答には使われていません。

回答の正しさは変更前後で変わりませんでした。4回とも、コンパクションは同じセッション内で古い履歴を要約して詰めること、セッションをまたぐメモリは外部に保存して次のセッションで読み戻すこと（p.39）、日々のメモは基準を超えたものだけが長期メモリへ移ること（p.40）を答えています。変更後の2回目は、後半を「OpenClaw の実装例を確認してみてください」というヒントの形で書いていました。前後ページの追加との関係は確認できていません。

### 改善した例と、残る失敗・制約

- 根拠が増えた例：Q3 の p.39 は、通常の検索1回目（「問題設定の工程」）では返らず、前後ページとして初めて取得できました。ただし、変更前のモデルは2回目の検索で p.39 を自力で取得していたので、今回の3問では、前後ページの追加によって回答が正しくなった例はありませんでした。
- 不要な情報が増えた例：Q1・Q2 では、追加した前後ページ（Q1 で6ページ、Q2 で6ページ）がどれも回答に使われず、入力トークンが約1.8倍になりました。検索上位5件のうち、もともと質問と関係の薄いヒット（Q1 の p.60・61、Q3 の p.62・47・34 など）の前後まで付くためです。
- 残る失敗：Q3 では、まとめて多くのページが返ったことでモデルが追加の検索をしなくなり、p.40・43 を取得できませんでした。この解釈は2回の実行で同じ挙動が出たことからの推測で、検索回数が減った原因が返ったページ数なのか、docstring の変更なのかは切り分けていません。
- 制約：各条件2回ずつの実行なので、時間の差やモデルの回答のばらつきについて結論は出せません。対象は第1〜3回の本講義だけです。

### 気づき・疑問

前後ページを付けて効くのは、答えが「（続き）」のように連続したページに分かれていて、検索がその片方だけを取ったときです。今回の資料では、p.37〜43 のように続きが3ページ以上に広がる箇所があり、前後1ページでは足りませんでした。かといって window を広げると、関係の薄いヒットの前後も一緒に増えます。次に試すなら、前後ページを付ける対象を上位1〜2件や距離が一定以下のヒットに絞るか、「（続き）」を含むタイトルや同じ章（`section`）だけを広げる方法を比べたいです。

もう1つの疑問は、取得量を増やすと、モデルが検索語を変えて探し直す回数が減るのかどうかです。Q3 では、変更前のモデルが2回目の検索で必要なページを自分で取りに行っており、取得処理で先回りして足すよりも結果が良くなりました。返す量と検索のやり直しのどちらに任せるかは、質問の種類ごとに評価セットで比べないと決められないと考えています。
